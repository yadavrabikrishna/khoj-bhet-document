# 1. Purpose and Scope

This document is the **authoritative written definition** of KHOJ BHET product flows.

It converts approved requirements and use cases into actionable process definitions that can be used by UX, architecture, implementation and testing.

**Scope:** 24 primary user flows (one per approved Use Case) plus 5 supporting process/state models, for a total catalogue of **29 flow artifacts**. Primary user flows use UF-XXX identifiers; supporting models use S-XX identifiers.

This document defines **what a flow does**. Whimsical diagrams are visual references derived from these definitions; no separate flow inventory or construction-specification document is maintained.

# 2. Flow Definition Standard

Every formal flow uses the same structure:

- **Goal**
- **Primary Actor**
- **Supporting Actors/Systems**
- **Entry Point**
- **Preconditions**
- **Main Flow**
- **Decision Points**
- **Alternate Flows**
- **Exception Flows**
- **Exit/Success State**
- **Related Use Case**
- **Related Requirements**
- **Whimsical Reference**

Whimsical may visualize a flow, but the Whimsical diagram must not become a second source of truth.

# 3. Formal User Flows

## UF-001 — Register Account

**Goal:** Allow a visitor to create a verified marketplace account.

**Primary Actor:** Visitor.

**Supporting Actors/Systems:** Authentication, user/profile, verification and notification services.

**Entry Point:** Visitor selects Register.

**Preconditions:** Registration is available and the visitor is not authenticated.

**Main Flow:**

1. Visitor selects Register.
2. System displays required registration information and verification method.
3. Visitor enters the required information.
4. System validates the information.
5. System checks whether the identifier is already registered.
6. System creates a pending verification record.
7. System sends the verification challenge.
8. Visitor submits the challenge.
9. System validates the challenge.
10. System activates the account.
11. System creates the initial user profile/security context.
12. System establishes the authenticated session where applicable.
13. System continues to onboarding or the appropriate destination.

**Decision Points:** Data valid? Identifier already registered? Verification successful? Registration permitted?

**Alternate Flows:** Resend verification; correct data; cancel registration; retry verification.

**Exception Flows:** Expired/invalid challenge; duplicate identifier; rate limit; service failure.

**Exit/Success State:** A verified active account exists.

**Related Use Case:** UC-001 Register Account.

## UF-006 — Submit Listing

**Goal:** Move an eligible listing into the applicable validation/review/publication process.

**Primary Actor:** Poster.

**Supporting Actors/Systems:** Listing, validation, moderation/publication and notification services.

**Entry Point:** Poster selects Submit on an eligible draft.

**Preconditions:** Listing exists under the poster's authorized scope.

**Main Flow:**

1. System verifies authorization and current state.
2. Poster selects Submit.
3. System validates required fields, category attributes, media and location.
4. System evaluates applicable business and publication rules.
5. System determines the next permitted lifecycle state.
6. System records submission.
7. System routes the listing to Review; direct publication from submission is not permitted.
8. System notifies the poster that the listing is under review.

**Decision Points:** Required data complete? Validation successful? Review outcome approved, rejected, or returned for correction?

**Alternate Flows:** Return to edit; cancel before submission; remain as draft when validation fails.

**Exception Flows:** Authorization failure; concurrent state change; validation/service failure.

**Exit/Success State:** Listing enters Review and can become Published only after the required review is approved.

**Related Use Case:** UC-006 Submit Listing.

**Whimsical:** [UF-006 — Submit Listing](https://whimsical.com/uf-006-submit-listing-GYCSJ5BmfwcajAYFr7ygGb).

**Rule:** Every listing requires review/moderation before publication, as defined in 08. Product & Business Rules.

## UF-007 — Publish Listing

**Goal:** Make an eligible listing publicly discoverable after all publication conditions are satisfied.

**Primary Actor:** Authorized Poster / System.

**Supporting Actors/Systems:** Validation, moderation, listing/index and notification services.

**Entry Point:** Submitted listing reaches the publication decision point.

**Preconditions:** Submission exists and publication conditions can be evaluated.

**Main Flow:**

1. System verifies listing state and authorization context.
2. System validates required fields, category data, media and location.
3. System routes the listing through the required review/moderation process.
4. If review returns the listing for correction, it remains unpublished until resubmitted and approved.
5. If review rejects the listing, it remains unpublished and the applicable outcome is recorded.
6. Only after review approval and satisfaction of all publication conditions does the system change state to Published.
7. System updates discovery/index visibility.
8. System records publication and sends applicable notification.

**Decision Points:** Validation successful? Review approved? Listing still eligible?

**Alternate Flows:** Return for correction; reject; remain pending; retry after temporary failure.

**Exception Flows:** Validation failure; moderation failure; listing becomes ineligible; indexing/service failure.

**Exit/Success State:** Listing is Published and discoverable according to visibility rules.

**Related Use Case:** UC-007 Publish Listing.

**Whimsical:** [UF-007 — Publish Listing](https://whimsical.com/uf-007-publish-listing-2e12DzWvdnCiA67j5Uikgf).

**Rule:** Every listing requires review/moderation before publication. The policy is resolved in 08. Product & Business Rules; this flow must not permit direct publication.

## UF-008 — Pause Listing

**Goal:** Allow an authorized poster to temporarily pause an eligible listing and later restore it when permitted.

**Primary Actor:** Poster.

**Supporting Actors/Systems:** Listing, discovery/index and notification services.

**Entry Point:** Poster opens listing management.

**Preconditions:** User is authenticated and the requested transition is permitted.

**Main Flow — Pause:**

1. System verifies authorization and state.
2. Poster selects Pause.
3. System validates the transition.
4. System changes state to Paused.
5. System removes the listing from normal active discovery where required.
6. System records the transition.

**Main Flow — Resume:**

1. Poster selects Resume on an eligible paused listing.
2. System verifies authorization and state.
3. System revalidates current publication conditions.
4. System changes the listing to Published or another permitted state.
5. System restores discovery according to visibility rules.
6. System records the transition.

**Decision Points:** Authorized? Transition permitted? Resume conditions satisfied?

**Alternate Flows:** Cancel; resume requires additional review.

**Exception Flows:** Unauthorized action; invalid transition; concurrent change; service failure.

**Exit/Success State:** Listing is Paused or restored to the appropriate active state.

**Related Use Case:** UC-008 Pause Listing.

**Whimsical:** [UF-008 — Pause Listing](https://whimsical.com/uf-008-pause-listing-Dd8JuboEuAN6vLAcXiuUCV).

**Main Flow:**

1. System verifies authentication and business-management authorization.
2. System displays the current business representation.
3. User creates or edits permitted information.
4. System validates business data and representation rules.
5. User saves.
6. System persists the business representation.
7. System records the relevant change.
8. System displays the updated business context.
9. Member management remains available through UF-024.

**Decision Points:** Authorized? Data valid? Business state permits change?

**Alternate Flows:** Create business representation; update profile/settings; cancel.

**Exception Flows:** Permission failure; invalid data; restricted business state; service failure.

**Exit/Success State:** Business representation is updated consistently.

**Related Use Case:** UC-023 Manage Business.

**Whimsical:** [UF-023 — Manage Business](https://whimsical.com/uf-023-manage-business-2paTv9xCZvk5iYQgEyDsoo?ref=mcp).

## UF-024 — Manage Business Members

**Goal:** Allow an authorized business owner/admin to manage members and their business access.

**Primary Actor:** Business Owner / Business Admin.

**Supporting Actors/Systems:** Authentication, authorization, business, notification and audit services.

**Entry Point:** Authorized actor opens business member management.

**Preconditions:** Actor is authenticated; business exists; actor has member-management permission.

**Main Flow:**

1. System verifies business context and authorization.
2. System displays current members and permitted actions.
3. Actor selects invite/add, update access or remove member.
4. System validates the requested change.
5. System applies membership/access change.
6. System records the administrative event.
7. System notifies the affected member where applicable.
8. System displays updated membership.

**Decision Points:** Actor authorized? Action permitted for actor role? Member/invitation already exists? Business state permits change?

**Alternate Flows:** Invite; resend invitation; change role/access; remove member; cancel.

**Exception Flows:** Duplicate invitation; insufficient permission; business restriction; service failure.

**Exit/Success State:** Membership and access reflect the validated change.

**Related Use Case:** UC-024 Manage Business Members.

**Related Flow:** UF-023 Manage Business.

**Whimsical:** [UF-024 — Manage Business Members](https://whimsical.com/uf-024-manage-business-members-Tb8GAo8m72EggyoBAt32YD?ref=mcp).
