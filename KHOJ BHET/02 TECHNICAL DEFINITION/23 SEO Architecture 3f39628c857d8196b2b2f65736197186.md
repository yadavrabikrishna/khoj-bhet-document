## 1. Purpose

This document defines the search-engine optimization architecture for KHOJ BHET across the public web application, listing pages, category pages, location pages, public seller/business pages, media assets, crawl controls, structured data, sitemaps, canonicalization, internationalization, and AI/LLM discoverability.

SEO is an architectural concern, not merely page metadata. Public discoverability remains subordinate to listing visibility, privacy, authorization, moderation, subscription, and security rules.

## 2. SEO Objectives

1. Make eligible public marketplace content discoverable.
2. Produce stable, indexable, canonical URLs.
3. Support Nepali and English, including Devanagari and mixed-language content.
4. Provide useful category, locality, and listing landing pages without uncontrolled URL combinations.
5. Support search engines, image search, rich results, and standards-compliant crawlers.
6. Provide controlled machine-readable context through structured data and `llms.txt`.
7. Prevent private, paid-only, unpublished, expired, deleted, suspended, duplicate, or unauthorized content from becoming indexable.
8. Remain compatible with the MySQL-first Search Architecture and Frontend Architecture.

## 2.1 Canonical Public Route Contract

The public web route convention is:

- Listing: `/listing/{slug}-{public-id}`.
- Category: `/category/{category-slug}`.
- Approved locality: `/location/{location-slug}`.
- Eligible public business: `/business/{business-slug}`.

The route slug is descriptive, while the stable public ID identifies the resource. A redirect after a slug change is permitted only when the current public ID resolves to an eligible resource and a durable slug-history/canonical-resolution strategy exists. Document 13 currently does not establish a location-slug registry; location landing pages remain non-implementable until their stable slug source and resolver are specified. Do not invent URLs from integer IDs.

## 3. Core Principles

- Public visibility is the prerequisite for indexing.
- `noindex` is not an authorization mechanism.
- Canonicalization is deterministic.
- One logical resource has one preferred canonical URL.
- SEO routes never expose protected exact location/contact data.
- Crawlers receive the same public business truth as ordinary unauthenticated visitors.
- Structured data describes visible, truthful content.
- Arbitrary filter combinations are not independently indexable by default.
- Sitemap membership is an explicit eligibility decision.
- Robots is crawl control, not security.
- AI/LLM guidance never exposes private data.
- SEO metadata comes from authoritative domain data.

## 4. SEO Scope

SEO covers the public home page, category/subcategory pages, public listing detail pages, approved locality pages, eligible public seller/business pages, public editorial/help/legal pages, public media where independently indexable, XML sitemaps, `robots.txt`, `llms.txt`, canonical/alternate URLs, social metadata, and JSON-LD structured data.

Authenticated dashboards, admin panels, private messages, account pages, saved searches, payment pages, protected media, and private APIs are outside the public SEO surface.

## 5. Public SEO Eligibility

A resource is indexable only when its public visibility and SEO policy permit it. For listings, minimum conditions include published status, public approval, not deleted/suspended, valid category/subcategory, valid canonical data, crawlable public rendering, and sufficient useful public content.

Subscription status must not by itself make a private resource public. A public listing must never expose premium fields merely because it is indexable.

## 6. Visibility Classes

### 6.1 Indexable

Public, canonical, useful pages intended for search discovery.

### 6.2 Crawlable but Non-Indexable

Reachable pages that should not enter indexes; use page-level `noindex` where appropriate.

### 6.3 Disallowed for Crawling

Operational or non-public paths that should not be routinely crawled.

### 6.4 Private

Authentication/authorization protected resources. Robots rules do not protect these resources; server authorization does.

## 7. Public URL Architecture

Recommended patterns:

- `/`
- `/category/{category-slug}`
- `/category/{category-slug}/{subcategory-slug}`
- `/listing/{listing-slug}-{public-id}`
- `/location/{location-slug}` for approved location landing pages
- `/business/{business-slug}` where public indexing is permitted

The final route convention is an implementation contract and must be consistent across backend, frontend, sitemap, canonical, structured data, and redirect logic.

Public IDs should avoid exposing internal database sequencing when practical. URL identifiers are presentation identifiers, not authorization credentials.

## 8. Slug Architecture

Slugs derive from authoritative names and are normalized deterministically.

Rules:

- Unicode-safe Nepali/Devanagari handling;
- lowercase Latin normalization where applicable;
- collapse repeated separators;
- remove unsafe URL characters;
- preserve meaningful words;
- enforce uniqueness within route scope;
- resolve the stable public ID from listing URLs and redirect stale slug suffixes to the current canonical slug while the resource remains public.

A dedicated slug-history table is not required for listing redirects when the URL contains a stable public ID and the resolver can fetch the current canonical slug. Location/business/category routes still require a deterministic slug source and resolver; add persistent slug fields or a registry only through the approved schema contract.

SEO slug normalization must not corrupt Devanagari text.

## 9. Canonical URL Architecture

Every indexable page exposes exactly one preferred canonical URL.

Canonical generation must:

1. derive from the authoritative route;
2. use HTTPS in production;
3. use the public host;
4. remove tracking/session parameters;
5. normalize trailing-slash and host policy;
6. avoid arbitrary filter parameters;
7. match sitemap URLs;
8. remain consistent with redirects.

A canonical tag must never point to an unavailable or non-indexable page.

## 10. Redirects and URL Changes

Use permanent redirects for durable route/slug/host changes where appropriate. Prevent redirect chains and loops. Deleted resources follow an explicit lifecycle policy rather than being redirected to unrelated content by default.

## 11. robots.txt

`robots.txt` is a generated public resource at the canonical web host.

It must:

- declare authoritative sitemap URL(s);
- disallow clearly non-public crawler paths where useful;
- avoid blocking resources required to render public pages;
- never be treated as access control;
- remain synchronized with public route architecture.

Potential disallow areas include authenticated routes, admin routes, internal API paths, checkout/payment flows, and operational endpoints. Exact rules must be validated against the final route table.

## 12. Robots Integration

Robots policy must be centrally generated or version-controlled with public route policy, not independently maintained across layers. Production must use the same canonical host and sitemap policy used by canonical URLs.

Staging/test environments must have explicit non-indexing protection so they cannot accidentally become authoritative indexed properties.

## 13. Meta Robots

The application supports page-level directives such as `index,follow` and `noindex,follow` according to server-derived page eligibility. `noindex` must never be controlled by untrusted client parameters.

## 14. Faceted Navigation

Arbitrary marketplace filter combinations are not independently indexable by default. This includes arbitrary price ranges, sort order, transient UI filters, arbitrary attribute combinations, tracking parameters, saved-search parameters, and internal query parameters.

Only deliberately curated landing pages may be indexable, such as approved category + locality combinations with stable content and sufficient value.

## 15. Pagination

Pagination must provide stable navigation without creating unnecessary duplicate indexable URLs. Internal search APIs use deterministic, signed opaque cursor pagination as defined by Document 21. Do not create crawlable `?page=N` links that imply the API supports page-number pagination when it does not. For V1, index only explicitly approved canonical category/location/listing routes; keep search/filter/cursor URLs non-indexable unless a stable page-number API contract is separately approved. If crawlable pagination is later required, define a stable SEO page route and mapping to the backend API without exposing cursor tokens in canonical URLs.

Pagination must never expose stale or newly ineligible listings.

## 16. Category/Subcategory SEO

Category pages derive from the authoritative CAT-001–CAT-025 catalogue. Indexable pages should have unique titles/descriptions, canonical URLs, valid indexability state, concise category information, relevant child links, and qualifying public listing links.

SEO must never invent categories outside the authoritative catalogue.

## 17. Listing SEO

The public listing page is the primary marketplace SEO unit. Subject to public visibility rules it may expose title, category/subcategory, public description, approximate location context, public price, public facilities/attributes, public status, public media, and permitted seller/business identity.

It must never expose protected exact address, private contact information, or premium-only fields merely for SEO.

## 18. Listing Lifecycle SEO

Lifecycle and expiry jointly determine public availability. Every public detail read, search result, recommendation, sitemap feed, structured-data response, SSR render, and cached representation must evaluate both the approved lifecycle/visibility state and `expires_at > UTC_NOW()` at read time; scheduler status alone is insufficient. The expiry scheduler is a cleanup/transition mechanism, not the security or visibility boundary.

V1 unavailable-listing policy: expired listings return a non-disclosing 404 on public detail routes because they may be renewed later; never expose restricted fields in a 404/redirect response. Never-published, paused, suspended, or unauthorized listings also return a non-disclosing 404 to public callers. Use 410 only for a permanently removed URL when the removal is irreversible under the product policy and no restoration/renewal path exists. Owners may access their own authorized management representation separately.

At cache/ISR/CDN layers, set a maximum freshness interval that cannot leave a listing public past its expiry, and invalidate/revalidate immediately on publish, pause, archive, moderation, deletion, renewal, or visibility changes. Sold/rented historical pages are a future policy choice and are not implicitly indexable.

## 19. Location SEO

Location SEO follows the project's postal code, municipality, locality/chowk, and approved geographic hierarchy. Exact private coordinates and restricted addresses must never be exposed.

Only approved, useful location landing pages are indexable. Arbitrary coordinate, radius, map viewport, and filter combinations are not indexable landing pages.

## 20. Business/Seller SEO

Public seller/business pages may be indexable only where business rules explicitly permit. Public identity and listings may be shown without exposing private account/security data or private contact information.

## 21. Structured Data

JSON-LD is the preferred structured-data format. It is generated from the same authoritative data used to render visible content.

Potential schema types include `WebSite`, `Organization`, `BreadcrumbList`, `ItemList`, `Product`, `Offer`, appropriate real-estate schemas where verified, and `LocalBusiness` for qualifying public businesses.

Do not emit fabricated, hidden, unsupported, or contradictory properties.

## 22. Breadcrumbs

Breadcrumbs should mirror public information hierarchy, for example `Home → Category → Subcategory → Listing` or `Home → Location → Category → Listing`. Breadcrumb URLs must be canonical and public.

## 23. Open Graph and Social Metadata

Public pages should provide title, description, canonical URL, representative public image, site identity, and locale where supported. Only public media variants may be used.

## 24. Image SEO

Public listing images use optimized public variants and descriptive alternative text where appropriate. Media processing follows Document 20, including removal/sanitization of sensitive EXIF metadata where required. Private originals and protected media must never enter SEO metadata.

## 25. Sitemap Architecture

XML sitemaps are generated by **Next.js from existing documented public API and reference-data responses**. V1 does not introduce a dedicated backend sitemap-feed endpoint. The generator must use the documented opaque cursor internally to enumerate eligible public listings; it must not publish cursor values or invent crawlable `?page=N` API URLs. Only canonical, indexable resources returned as publicly eligible by the API may be emitted. Revalidate or invalidate affected sitemap output after publication, unpublication, moderation, deletion, expiration, renewal, visibility changes, and canonical changes. If an existing API cannot provide enough information to enumerate a resource class safely, do not invent an endpoint: raise an API contract change before implementation. Location sitemap entries remain blocked until Document 13/14 define a stable location slug source and resolver. Recommended groups:

- sitemap index;
- static/public pages;
- categories;
- locations;
- listings;
- eligible public business profiles;
- optionally public images/media where justified.

Only canonical, indexable URLs belong in sitemaps.

## 26. Sitemap Freshness

Publication, unpublication, deletion, moderation, expiration, canonical changes, and other visibility transitions must invalidate or refresh affected sitemap representations. Sitemap modification timestamps must represent meaningful content changes, not request time.

## 27. Sitemap Security

Sitemaps are public and therefore may contain only public URLs. Never include authenticated URLs, signed private media URLs, exact private-location routes, contact endpoints, credentials, or temporary tokens.

## 28. Search Engine Rendering

SEO-critical content must be available in server-rendered or otherwise crawlable HTML. JavaScript may enhance the experience but must not be the sole source of listing identity, title, description, canonical URL, or primary navigation.

## 29. Frontend Integration

Document 15 defines frontend SEO responsibilities. Frontend rendering must consume authoritative SEO metadata rather than independently deciding indexability.

The SEO metadata contract should provide canonical URL, title, description, robots directive, Open Graph metadata, structured-data payload, breadcrumb data, and alternate URLs where applicable.

## 30. API Boundary

The REST API is not the primary indexing surface. SEO pages may consume API/domain services, but the same visibility and authorization rules apply. Browser clients must not require privileged API credentials to render public SEO pages.

Internal search, authenticated, mutation, and private APIs must never become indexable merely because they are technically reachable.

## 31. Search Architecture Integration

Document 21 governs search eligibility, filtering, ranking, and public result boundaries. SEO landing pages may consume search results only after eligibility is enforced.

SEO must never bypass visibility, expose exact private location/contact information, index unpublished resources, or create an alternate authorization path.

## 32. Media Storage Integration

Document 20 governs public/private media, variants, lifecycle, and access control. SEO references only public media variants. Private media must not appear in `og:image`, JSON-LD, sitemap entries, HTML image tags, or public preload resources.

## 33. Notification Boundary

Notification deep links do not automatically become SEO routes. Notification-specific/private URLs remain non-indexable.

## 34. Authentication Boundary

Public SEO pages must not require authentication. Protected pages remain protected even when crawlers request them directly. Login, account, payment, admin, and private messaging surfaces are non-SEO unless explicitly designated otherwise.

## 35. Security Boundary

SEO must respect Documents 18 and 19.

- robots is not access control;
- `noindex` is not access control;
- canonical URLs are not authorization credentials;
- sitemap URLs are public by definition;
- structured data cannot disclose protected fields;
- CDN/cache configuration cannot bypass visibility checks;
- stale SEO pages must not resurrect removed content;
- crawler requests receive normal security controls.

## 36. Duplicate Content Controls

Duplicate content can arise from slug aliases, query parameters, sorting, tracking parameters, alternate routes, duplicate category paths, location aliases, and pagination variants. Controls are canonical URLs, redirects, controlled parameter handling, curated landing pages, and consistent internal linking.

## 37. Internationalization

V1 supports Nepali and English content patterns. Distinguish interface language, listing language, transliteration/search normalization, and canonical resource identity.

If separate localized URL variants are implemented, use valid `hreflang` relationships and ensure each alternate is a genuine equivalent page.

## 38. Nepali/Devanagari SEO

Unicode must be preserved correctly in titles, descriptions, slugs where selected, structured data, XML, HTML, and metadata. Search normalization may be more aggressive than canonical URL normalization; the two concerns remain separate.

## 39. Internal Linking

Public pages should link logically to parent categories, subcategories, approved locations, related public listings, public seller/business pages, and relevant informational pages. Links must derive from authoritative relationships and must not create unbounded crawl graphs.

## 40. Orphan Page Prevention

Important indexable pages need a discoverable internal-link path from another public page, sitemap, or both. A technically indexable but undiscoverable listing is an SEO quality defect.

## 41. Thin Content Controls

Avoid automatically indexing empty categories, empty location combinations, arbitrary filters, duplicate seller pages, unstable search results, or pages containing only navigation chrome. Indexability is an explicit product/content decision, not a simplistic word-count threshold.

## 42. Crawl Budget

Crawl efficiency is managed through controlled parameters, canonicalization, robots policy, sitemap hygiene, stable pagination, duplicate-route removal, cache-friendly pages, and bounded faceted navigation. Do not use cloaking or deceptive crawler content.

## 43. AI/LLM Discoverability

KHOJ BHET provides a controlled public machine-readable discovery layer for AI/LLM systems without treating it as a replacement for robots, sitemap, canonical, or normal web standards.

The architecture includes `/llms.txt` at the canonical site root where deployed. It may describe KHOJ BHET, important public sections, official category/location resources, help/documentation resources, public usage guidance, and preferred public URLs.

It must not contain private data, authentication material, API secrets, user contact data, exact restricted locations, or unapproved bulk listing payloads.

## 44. llms.txt Integration

`/llms.txt` must be generated or maintained from the same public information architecture as the website.

Requirements:

- canonical HTTPS URL;
- UTF-8 encoding;
- stable public links;
- concise descriptions;
- no session tokens;
- no signed private URLs;
- no unpublished content;
- deployment/version control;
- review whenever public routes change.

An expanded AI-specific resource introduced later must follow the same public-data and authorization rules.

## 45. AI/LLM Crawler Policy

Robots directives may express preferences for supported user agents, but crawler identity must never be trusted as a security mechanism. Normal authorization and public/private route boundaries always apply.

LLM discoverability is an explicit content-policy choice, not an implicit license to expose private marketplace information.

## 46. Machine-Readable Consistency

Structured data, visible HTML, canonical metadata, sitemap entries, and `llms.txt` should describe the same public resource identity. Contradictory machine-readable representations are an SEO defect.

## 47. SEO Metadata Service

SEO metadata should be centralized behind a reusable application boundary, such as an SEO Metadata/SEO Rendering service.

Responsibilities:

- determine eligibility;
- generate canonical URL;
- generate title/description;
- generate robots directive;
- generate structured data;
- generate breadcrumbs;
- expose Open Graph metadata;
- expose alternate-language metadata where applicable.

Controllers/components should consume this service rather than reimplement SEO policy.

## 48. Cache/CDN Integration

Public SEO pages may be cached, but cache keys must represent every factor that changes public output. Invalidate affected representations on publication, update, moderation changes, deletion, expiration, media replacement, category/location changes, and canonical URL changes.

Protected pages must never be served from shared public cache.

## 49. Observability

Track sitemap failures/freshness, unexpected 404/410 rates, redirect loops/chains, canonical mismatches, indexability-policy failures, structured-data errors, robots/llms availability, public rendering failures, orphan indexable pages, and stale cached SEO content.

Do not log private query data or protected listing fields unnecessarily.

## 50. SEO Testing

Automated tests must cover canonical generation, slug normalization, robots output, noindex rules, sitemap inclusion/exclusion, listing lifecycle transitions, structured-data validity, protected-field exclusion, public/private media separation, duplicate-route redirects, pagination, localization/hreflang where implemented, `llms.txt`, staging noindex, and crawlable HTML.

## 53. Implementation Rules

1. Build SEO policy once and reuse it across web routes, sitemap generation, metadata, structured data, and `llms.txt`.
2. Keep SEO eligibility server-authoritative.
3. Never use robots.txt to protect sensitive resources.
4. Never expose premium/private fields in machine-readable metadata.
5. Never index arbitrary search/filter combinations by default.
6. Keep sitemap and canonical URL generation deterministic.
7. Use the authoritative catalogue and location model.
8. Keep public SEO content separate from authenticated application surfaces.
9. Make AI/LLM discoverability explicit and controlled.
10. Test SEO state transitions as part of listing lifecycle tests.
11. Treat stale cached SEO output as a correctness defect.
12. Ensure every indexable page has a stable canonical identity.

## 54. Security Invariants

1. SEO never grants authorization.
2. Robots directives never protect private data.
3. `noindex` never protects private data.
4. Sitemaps contain only approved public URLs.
5. Canonical URLs never bypass access control.
6. Structured data never contains protected fields.
7. `llms.txt` never contains secrets or private user data.
8. Public SEO pages never reveal exact restricted locations or private contacts.
9. Search engines and AI crawlers receive only data permitted by public web policy.
10. Stale caches never resurrect unpublished or deleted content.
11. Client-controlled query parameters cannot force indexability.
12. SEO rendering cannot bypass moderation, subscription, or lifecycle policy.
13. Public media used for SEO satisfies Media & File Storage access policy.
14. SEO routes cannot become an alternate authorization path.

## TV-04 Location Slug Gate — MVP Safety Decision (2026-10-18)

**Decision for implementation sequencing:** Do not publish or sitemap location landing pages until a stable public slug and resolver are represented in the approved physical schema and covered by tests. This is a release gate, not permission to synthesize URLs from integer database IDs.

**Required implementation contract before enabling location SEO:**

1. Limit the initial location landing-page scope to explicitly approved location levels; do not automatically generate pages for every ward, locality, landmark or named place.
2. Define a stable canonical public identifier and normalized slug source in Document 13. The identifier must not expose sequential internal IDs. Slugs must be unique for the chosen route shape and handle collisions deterministically.
3. Define the resolver and canonical response in Document 14. Unknown, ambiguous, disabled or non-approved locations return a non-disclosing 404; valid aliases/renames may redirect only when the canonical target is unambiguous.
4. Define Unicode-safe normalization for Nepali/Devanagari and Latin names, collision policy, rename behavior and permanent redirect behavior. Do not transliterate Devanagari without an approved policy.
5. Validate that API results, page canonical tags, structured data, robots policy and XML sitemap use the same canonical URL.
6. Regenerate DBML, Laravel migrations and validation SQL as one reviewed artifact set if schema fields/tables change. Run uniqueness, collision, parent-scope, rename and resolver tests before enabling pages.

**Status remains BLOCKED:** this decision establishes the safety gate, not the final schema. Final physical design and artifact regeneration require review of the current Gate #14 source artifacts. Until then, location landing pages remain disabled/non-indexable and must not be included in sitemaps.
