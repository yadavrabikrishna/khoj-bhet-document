## 1. Purpose

This document defines how KHOJ BHET validates, packages, promotes, deploys, and verifies software changes. It establishes CI/CD responsibilities and quality gates while leaving hosting topology, production sizing, networking, and deployment-specific configuration to Document 26.

CI/CD must make delivery repeatable, auditable, secure, and recoverable. Automation must not bypass code review, QA acceptance criteria, migration review, or release authorization.

## 2. Scope

The pipeline covers components that are actually adopted and maintained by the project:

- Laravel 13 backend and REST API.
- FilamentPHP 5 administration.
- Next.js public web application.
- React Native + Expo mobile application and build artifacts.
- MySQL migrations, schema validation, and reference data.
- API/OpenAPI 3.1 contract validation when the canonical artifact is available.
- Background jobs, scheduled tasks, media processing, and integration adapters that are implemented.
- Infrastructure configuration, deployment manifests, and operational scripts maintained in version control.

Firebase Authentication and payment, push, email, or storage providers may require separate sandbox checks. CI must not assume every external service is available in every run.

## 3. Principles

1. **Automate repeatable checks:** builds, formatting, static analysis, tests, dependency scans, and artifact validation run consistently.
2. **Review before merge:** successful automation does not replace human review.
3. **Immutable artifacts:** build once for a release candidate and promote the same artifact between environments where feasible.
4. **Environment separation:** development, CI, staging, and production credentials and data remain isolated.
5. **Least privilege:** each workflow receives only the permissions required for its job.
6. **Fail safely:** a failed mandatory gate stops promotion; no silent bypasses.
7. **Traceability:** production deployments map to a reviewed commit, release identifier, artifact, test evidence, and approval.
8. **Reproducibility:** pin runtimes and build tools; use lockfiles and documented version policies.
9. **Supply-chain integrity:** protect dependencies, build credentials, workflow definitions, artifacts, and deployment permissions.
10. **Recovery by design:** deployments include health verification and a documented failure response.
11. **Cost-aware automation:** fast checks run on pull requests; slower device, performance, and external sandbox suites run at appropriate stages.
12. **No premature vendor lock-in:** choose the CI provider and deployment platform explicitly; examples remain illustrative until approved.

## 4. Logical Delivery Flow

1. Developer creates a branch and submits a pull request.
2. CI runs formatting, linting, static analysis, focused tests, MySQL integration tests, contract validation, and security checks.
3. Reviewers approve the change after required gates pass.
4. A protected-branch merge triggers complete applicable tests and build validation.
5. A versioned release artifact is built, scanned, and associated with its source commit.
6. The approved artifact is deployed to staging and verified.
7. An authorized release owner approves production promotion.
8. Deployment health and critical workflows are verified and the result is recorded.
9. Failed deployments follow the approved rollback or forward-recovery runbook.

This is the target process, not a claim that these workflows are already implemented.

## 5. Repository and Workflow Boundaries

Document 28 defines branching, commit conventions, pull-request rules, and repository permissions. This document defines automated delivery stages.

Recommended workflow classes:

- **Pull request:** fast quality gates, focused tests, contract checks, security/dependency checks, and review evidence.
- **Protected-branch merge:** complete required test suite and build validation.
- **Release candidate/tag:** versioned artifact creation, provenance, applicable regression checks, staging deployment, and release approval.
- **Production promotion:** deploy the approved artifact, apply reviewed migrations, verify health, and record the result.
- **Scheduled maintenance:** dependency/security scans, lockfile checks, and slower tests.
- **Manual recovery:** restricted, audited rollback, redeployment, or migration-recovery procedures.

Untrusted pull-request code must never receive production secrets or privileged deployment tokens.

## 6. CI Pipeline Stages

### 6.1 Checkout and environment setup

- Check out the exact commit under test.
- Use supported, pinned runtime versions and reproducible dependency installation.
- Fail when dependency manifests and lockfiles are inconsistent.
- Set explicit working directories and environment variables.
- Never inherit production configuration into CI.
- Record commit SHA, branch/tag, runtime versions, and pipeline run identifier.

### 6.2 Formatting, linting, and static analysis

Run the formatter, linters, type checks, and static analysis adopted for each codebase. CI should check formatting rather than silently rewrite submitted code unless the workflow explicitly intends to do so.

Backend checks cover PHP/Laravel conventions. Web and mobile checks cover JavaScript/TypeScript, framework-specific linting, type checking, and build validation as applicable. Validate configuration and infrastructure files with suitable tools.

### 6.3 Automated tests

Document 24 is the source of truth for the testing strategy. At minimum, execute:

- Fast unit tests.
- Laravel feature tests and relevant integration tests.
- MySQL-backed migration/schema tests.
- API/OpenAPI contract validation when the canonical contract exists.
- Authorization and privacy regression tests for affected code.
- Frontend component tests and mobile logic tests adopted by the project.
- Critical end-to-end journeys at the designated stage.
- Web and mobile build checks.

SQLite-only tests do not replace MySQL integration coverage when correctness depends on MySQL behavior.

### 6.4 Dependency, secret, and supply-chain checks

- Scan direct and transitive dependencies for known vulnerabilities.
- Detect committed secrets and high-risk credentials.
- Validate lockfiles and package provenance where supported.
- Generate a software bill of materials (SBOM) for release artifacts when supported.
- Scan container images and deployment artifacts when containers are used.
- Review new packages for maintenance status, licensing compatibility, and supply-chain risk.
- Never print environment variables, access tokens, signing keys, Firebase service credentials, or payment secrets to logs.

Critical/high findings block release by default unless a documented exception records the risk owner, mitigation, expiry/review date, and approval.

### 6.5 Artifact validation

Fail builds for missing required files, invalid configuration, incompatible runtime requirements, malformed OpenAPI, or invalid deployment manifests. Artifacts must be versioned and traceable to the source commit. Store checksums and build metadata where supported. Do not embed environment-specific secrets or production-only configuration in artifacts.

## 7. Component-Specific Pipelines

### 7.1 Laravel backend and Filament

The backend pipeline should include dependency installation from the committed lockfile, style and static analysis checks, application bootstrap/configuration validation, unit and feature tests, MySQL integration tests, authorization/policy tests for API and Filament actions, applicable queue/cache/storage tests, production-mode checks, dependency audits, and artifact packaging.

Never run destructive production migrations from an unreviewed pull-request workflow. Production migration execution belongs to the approved deployment job and uses a narrowly scoped identity.

### 7.2 Next.js web application

Run lockfile-based dependency installation, linting, type checks, unit/component tests, production build, and applicable browser E2E tests. Validate SEO metadata, canonical URLs, public visibility, robots/sitemap generation, and structured data where these are implemented.

Server-only secrets must not leak into browser bundles. Preview deployments must not accidentally index private or unfinished content.

### 7.3 React Native + Expo mobile application

Run dependency and lockfile checks, linting, type checks, unit/component tests, and Expo configuration validation. Build Android/iOS artifacts on compatible infrastructure. Where applicable, run simulator/device E2E tests and verify signing configuration using protected secret handling.

Separate internal/test builds from store-release builds. Control version/build numbers, signing-key access, release notes, API compatibility, and store-submission approval. Signing credentials must never be available to untrusted pull-request jobs.

### 7.4 Database changes

For every migration:

- Apply all migrations from a clean database using the supported MySQL version.
- Verify schema and constraints against Document 13 and approved schema artifacts.
- Test data transformations with synthetic fixtures.
- Assess lock duration, table size, index impact, and compatibility for risky changes.
- Prefer backward-compatible expand-and-contract changes for rolling deployments.
- Define a recovery path; a down migration is not automatically safe for production data.
- Ensure seeders cannot overwrite production user or business data.
- Keep schema/application compatibility explicit.

### 7.5 Containers and infrastructure configuration

If containers are adopted, build images with pinned base images, scan them, run as non-root where practical, minimize image contents, and keep secrets out of image layers. Validate Compose/Kubernetes/IaC manifests with relevant tooling.

If deployment is not container-based, apply equivalent validation to packages, server configuration, service definitions, and deployment scripts. This document does not mandate containers.

## 8. Environment Promotion

| Environment | Purpose | Data and secrets |
| --- | --- | --- |
| Local development | Developer feedback and debugging | Synthetic/local data; local-only secrets |
| CI/test | Repeatable automated verification | Ephemeral databases and fake/sandbox providers |
| Staging/pre-production | Production-like release validation | Isolated test data and sandbox credentials |
| Production | Real users and transactions | Production data and restricted production secrets |

Promotion rules:

- Do not promote when mandatory checks fail, are missing, or are improperly waived.
- Use the same release artifact for staging and production when feasible.
- Inject environment-specific configuration at deployment time and validate it without exposing secret values.
- Restrict production access to approved deployment identities and operators.
- Do not copy production data into CI or staging without explicit approval and approved masking/minimization.
- Protect staging and preview environments from indexing and use isolated callback URLs.
- Verify provider webhooks, Firebase settings, storage destinations, CORS origins, and API base URLs for each environment.

## 9. Secrets and Identity Management

Secrets include database credentials, application keys, Firebase service credentials, payment-provider credentials, webhook signing secrets, push credentials, mobile signing keys, and deployment tokens.

Required controls:

- Store secrets in the selected CI secret store or approved secret manager.
- Use separate credentials per environment and provider sandbox.
- Prefer short-lived workload identity or scoped tokens where supported.
- Limit workflow permissions and token scope to the minimum required.
- Rotate credentials after suspected exposure, access changes, or provider/security requirements.
- Mask secrets in logs and avoid echoing commands that expand sensitive values.
- Never commit real-secret environment files, private keys, service-account JSON, signing keys, or database passwords.
- Keep production credentials unavailable to untrusted branches and forked pull requests.
- Audit and remove obsolete secrets and unused workflow permissions.
- Document emergency credential revocation and rotation in operational runbooks.

## 10. Deployment Strategy

Document 26 selects the actual deployment method. Depending on hosting model and risk, deployment may use rolling, blue-green, canary, or maintenance-window strategies. Do not promise zero downtime unless architecture, schema changes, and infrastructure have been designed and tested for it.

A deployment run should:

1. Identify the approved release tag/commit and artifact digest.
2. Confirm mandatory checks and approvals.
3. Verify backup/recovery readiness for persistent-data changes.
4. Check target environment, secret references, capacity, and dependency health.
5. Apply compatible migrations in the approved order.
6. Deploy the artifact and restart/reload only required services.
7. Run readiness and smoke tests.
8. Observe errors, latency, queues, and critical business signals.
9. Record success or failure and actions taken.
10. Retain the previous compatible artifact according to policy.

A process starting or a generic health endpoint responding does not prove that critical business workflows work.

## 11. Database and Application Compatibility

Deployments must account for mixed application versions during rolling updates, background jobs that outlive a deployment, mobile applications that remain installed for months, and external callbacks that arrive late or more than once.

For compatible schema evolution:

- Add nullable columns or tables before code requires them.
- Deploy code that supports old and new schema shapes where needed.
- Backfill data in bounded, observable batches.
- Switch reads/writes only after validation.
- Remove obsolete columns or behavior in a later release after compatibility is confirmed.

Irreversible or destructive changes require explicit migration review, a verified recovery plan, and documented approval. Mobile/API compatibility follows Document 14 and Document 17.

## 12. Release Gates and Approval

Production promotion requires:

- Approved pull request and protected-branch merge.
- Required CI jobs passing on the exact release commit.
- Current QA evidence per Document 24.
- No unresolved Critical/High security or data-integrity issue without a formally approved exception.
- Dependency, secret, and artifact checks completed.
- Database migration reviewed and recovery approach documented.
- Staging smoke/acceptance checks passed where staging is available.
- Release notes and known issues prepared.
- Required product/engineering approval recorded.
- Monitoring and operational response readiness confirmed for material changes.

Exceptions must identify the waived gate, reason, impact, compensating controls, approver, owner, and expiry/review date. A generic force-deploy switch is not a substitute for governance.

## 13. Rollback and Failed Deployment Handling

Rollback is not always safe after schema changes, irreversible data transformations, or external side effects. For each release, decide whether recovery means artifact rollback, feature-flag disablement, traffic shift, forward-fix, restore, or a coordinated sequence.

On failure:

1. Stop further promotion and preserve logs, artifact identifiers, and deployment events.
2. Determine whether user data or external side effects were affected.
3. Follow the approved runbook and notify the responsible owner.
4. Roll back only if the previous application is compatible with the current database and side effects.
5. Otherwise apply the approved forward-fix or recovery procedure.
6. Verify critical workflows and data integrity.
7. Record incident impact, root cause, and corrective actions.
8. Add regression tests for the failure mode.

Do not restore an entire production database merely because an application deployment failed; that could erase valid transactions created after the backup.

## 14. Scheduled Jobs, Queues, and Asynchronous Work

Where queues, scheduled jobs, or workers are enabled:

- Test retry, timeout, backoff, and failure behavior.
- Make jobs idempotent where retries or duplicate delivery are possible.
- Restart workers safely without abandoning or double-processing work.
- Coordinate scheduler execution to avoid duplicate schedules.
- Maintain compatibility for queued payloads during overlapping deployments.
- Monitor failed jobs, queue depth, and retry exhaustion.
- Test provider outages, delayed callbacks, duplicate events, and recovery.

The exact queue/cache infrastructure is determined by approved architecture and deployment documents.

## 15. Observability and Deployment Evidence

CI/CD should retain, where applicable:

- Commit SHA, branch/tag, workflow run ID, and build/runtime versions.
- Test results and code-quality reports.
- Dependency/security scan results and approved exceptions.
- Artifact identifier, checksum/digest, and provenance.
- Migration identifier and execution status without sensitive data.
- Target environment, deployment times, approver, and outcome.
- Smoke-test results and relevant health metrics.
- Rollback, forward-fix, or recovery actions.

Logs must be sanitized. Do not include Firebase tokens, passwords, signing keys, full payment credentials, or unnecessary personal data. Document 27 defines operational logging, monitoring, alerting, and backup requirements.

## 16. CI/CD Security Threats

Protect the pipeline against malicious dependency updates, compromised packages, secret exfiltration, untrusted pull requests accessing privileged tokens, workflow tampering, artifact substitution, overly broad permissions, injection through workflow inputs, unpinned third-party build steps, unauthorized production deployments, and preview-environment exposure.

Mitigations include protected branches/environments, least privilege, pinned actions and dependencies where supported, reviewed workflow changes, artifact digest verification, secret scanning, environment approvals, audit logs, and periodic access review.

## 17. Pipeline Performance and Reliability

Measure CI duration by stage, queue time, failure rate, flaky tests, cache hit rate, rerun frequency, and deployment lead time. Optimize with dependency caching, parallel execution, test selection, and reusable workflow components only when correctness is preserved.

Cache keys must include relevant lockfiles, runtime versions, and build inputs. Never cache credentials or mutable production data. A cache miss must not make a build incorrect; caches are optimizations, not sources of truth.

Track flaky tests with an owner and repair deadline. Quarantined tests require a reason, visibility, and review date; mandatory security or integrity tests must not be silently skipped.

## 18. Web and Mobile Release Controls

### Web

- Validate production build and environment configuration.
- Verify canonical URLs, metadata, sitemap/robots behavior, public/private visibility, and analytics configuration.
- Confirm preview/staging indexing protection and production domain configuration.
- Smoke test authentication, public listing pages, search, media, and core mutations after deployment.

### Mobile

- Control app version and build number.
- Protect Android keystores, iOS signing certificates/profiles, and store credentials.
- Separate internal distribution, beta testing, and public store submission.
- Validate API compatibility and critical journeys on supported devices.
- Record the exact binary and source commit associated with each store submission.
- Require explicit approval for public release; submission success does not guarantee store approval or availability.

## 19. Governance and Responsibilities

| Responsibility | Primary owner |
| --- | --- |
| Code correctness and tests | Author/developer |
| Pull-request review and design integrity | Reviewer/maintainer |
| Pipeline definitions and build reproducibility | Engineering/repository maintainer |
| QA acceptance evidence | QA owner or designated engineering reviewer |
| Production approval | Authorized release owner |
| Production deployment credentials | Restricted operations/deployment identity |
| Infrastructure and recovery procedures | Infrastructure owner, defined in Documents 26/27 |
| Risk exceptions | Named accountable owner with documented approval |

A small team may combine roles, but high-risk production changes should receive independent review where practical.

2. Add formatting, linting, static analysis, and fast unit tests.
3. Provision ephemeral MySQL for CI and enforce migration/integration tests.
4. Add API/OpenAPI contract validation and authorization regression tests.
5. Add dependency and secret scanning with a documented severity policy.
6. Build web and backend artifacts reproducibly; validate mobile build workflows separately.
7. Create isolated staging deployment and deterministic smoke tests.
8. Add protected production promotion, approvals, audit evidence, and recovery checks.
9. Add artifact provenance/SBOM, container/IaC scanning, and advanced performance/security suites as required.

Do not mark a stage complete until the workflow exists, has been exercised, and its result is verifiable in the repository or CI provider.

## 21. Open Decisions

The following are intentionally not assumed by this baseline:

- CI provider and repository hosting configuration.
- Production hosting topology, container orchestration, and deployment strategy.
- Exact runtime/tool versions after repository lockfiles are finalized.
- Hosting/build services for Next.js and Expo.
- Secret manager and workload identity capabilities.
- Numeric CI duration budgets and performance objectives.
- Artifact retention, rollback windows, and deployment approval roles.
- Whether containers, infrastructure-as-code, canary releases, or blue-green deployment are adopted.

Resolve these during implementation and in Documents 26–28. Update this document when the actual toolchain is selected.
